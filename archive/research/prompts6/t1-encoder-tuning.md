# Task t1-encoder-tuning (autonomous, about 100 minutes)

Goal: run controlled H.264 encoder tuning experiments for low-latency cloud-browser streaming, and produce recommended encoder settings with evidence. You may plan and iterate on your own within this scope.

Targets (from the brief): 1080p, 10 to 16 Mbps available (assume 12 Mbps nominal, also test 8 and 16), end-to-end latency P80 < 100 ms and P99 < 200 ms, H.264 decodable by Chrome 89 (Constrained Baseline or Main/High without B-frames; check what Chrome 89's WebRTC receiver negotiates; see research/g-h264-level.md and s8-chrome89.md). Encoder hardware: Intel UHD 630 with oneVPL/MSDK (the legacy runtime, API 1.35; see research/s7-onevpl-probe.md, which found that LowPower CBR 12 Mbps gives P50 5.9 ms and P99 11.7 ms encode latency, and that the driver turns LowDelayBRC off under CBR). Software fallback: OpenH264 (the current M1 chain uses it).

What to do:
1. Test content (store under C:\src\tmp\t1-encoder-tuning\media\): build 1080p raw sequences for the three scenarios: (a) web-page scrolling (render or record real pages scrolling at a realistic speed, e.g. by screenshotting a locally rendered long page with shifting offsets, or with Edge/Chrome headless screenshots), (b) video playback (a natural-video clip, e.g. a synthetic test clip via ffmpeg testsrc2/mandelbrot plus a real clip if one is freely available), (c) real-time game-like content (fast full-screen motion, e.g. ffmpeg-generated or a WebGL demo captured headless). About 10 to 20 s each at 60 fps (also 30 fps), NV12/YUV420. Install ffmpeg if missing.
2. A harness under tools/encoder-tuning/: start from the S7 probe program (find it via research/s7-onevpl-probe.md) and extend it to encode the sequences with configurable parameters, measuring per frame: encode latency, encoded size (bytes), frame type, and quality (PSNR and SSIM, or VMAF if easy) against the source. Also measure the bitstream "burstiness" that hurts latency: the per-frame size relative to the per-frame budget, the max frame size, and the estimated queueing delay at the given link rate (time to drain the frame at R Mbps with a simple leaky-bucket model).
3. The parameter space (iterate wisely, not exhaustively): rate control (CBR vs VBR vs QVBR/ICQ-like if supported; CBR with a small buffer, e.g. BufferSizeInKB about 1 to 2 frames' worth; MaxFrameSize caps), LowPower on/off, TargetUsage, GOP structure (infinite GOP plus intra refresh (IntRefType/IntRefCycleSize/IntRefQPDelta) vs periodic IDR), number of slices, profile/level, NumRefFrame (1 vs more), adaptive I/B off, LowDelayBRC (when it is accepted), scene-change handling, and 30 vs 60 fps at the same bitrate. Also OpenH264 as the baseline (rate-control modes, the screen-content vs camera usage type, threads, slices).
4. Analysis: for each scenario, give the best 2 to 3 configurations by a combined criterion: the 99th-percentile (encode latency + queueing delay) first, then quality. Explain the trade-offs (for example, intra refresh flattens IDR spikes; CBR buffer size vs quality on scrolling text).
5. Report: research/t1-encoder-tuning.md with the method, the tables, the recommended default config (exact oneVPL mfxVideoParam / ExtCodingOption field values) plus per-scenario overrides, the OpenH264 fallback config, caveats, and the open questions that need the real end-to-end chain to answer (e.g. receiver-side decode on Chrome 89). Keep raw CSVs under C:\src\tmp\t1-encoder-tuning\results\ and summarize them in the report.

Time-box: wrap up and write the report by 95 minutes even if experiments are incomplete. Partial results with clear notes beat none.

Final message: a 10-line summary (recommended configs, the key numbers, the caveats).
