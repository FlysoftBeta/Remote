# T1 — H.264 encoder tuning on Intel UHD 630

Date: 2026-10-26 (Asia/Singapore). Status: complete. Encoder/quality/queue experiments finished within the 95-minute deadline; receiver and end-to-end questions remain open.

## Scope and method

This is an isolated encoder experiment, not an end-to-end WebRTC acceptance test. The brief, video design, S7 probe, H.264 negotiation note and S8 receiver report were read first. Only `tools/encoder-tuning/` and this report are deliverables. All binaries, profiles, test media, encoded streams and raw results are under `C:/src/tmp/t1-encoder-tuning/`. No Chromium builds, product changes, commits or pushes were performed.

Hardware observed in this session: Intel Core i7-10700 (8 cores / 16 logical processors), Intel UHD Graphics 630, driver 30.0.100.9805. The actual CPU enumeration differs from the brief's older machine note. The dispatcher selects `mfxhw64`, API 1.35, D3D11, the Intel adapter's matching LUID. It uses the S7 libvpl 2.17 dispatcher, copied into this task's directory. The harness is derived from the S7 standalone probe's external allocator and D3D11 session setup.

Experiments run sequentially with below-normal process priority and affinity restricted to eight logical processors. Each main experiment receives a deterministic ten-second sequence: 600 frames at 60 fps or 300 at 30 fps. The 30 fps version selects every second source frame; it covers the same ten seconds. No warm-up is discarded. The first IDR, cold driver state, and all later spikes are included. Most exploration configurations have one run; shortlisted configurations pool 2400 frames each. Two 120-frame smoke checks are excluded from tables. These are short controlled experiments, with much less independent content than a production workload.

Input is packed NV12, 1920×1080, padded to a 1920×1088 D3D11 texture with a visible crop of 1920×1080. Input file reads, padding, upload and its GPU completion are outside the encode timer. Upload time is recorded separately. Encode latency is QPC immediately before `EncodeFrameAsync` through completed `SyncOperation`, including busy retries. `AsyncDepth=1` and `GopRefDist=1` prevent asynchronous backlog and B-frame reordering. OpenH264 takes the same pixels converted to I420 outside the timer; its timer surrounds `EncodeFrame`.

Source timestamps express nominal cadence. The main runs execute without pacing to isolate encoder service time; selected paced repeats check that limitation. CPU/GPU conversion, Chromium rendering contention, capture, RTP packetization/pacer/GCC, real network loss and jitter, decoder and display costs are outside this measurement. A modeled link is not a network experiment.

## Quality and queue definitions

Every successful full-length run is decoded with FFmpeg's software H.264 decoder and compared against the original NV12 reference. Software frame skips are expanded by holding the previous decoded picture, so quality covers every source instant rather than silently comparing only delivered frames. Per-frame PSNR and SSIM are saved in `*-psnr.log` and `*-ssim.log`, and joined to the timing rows in `*-metrics.csv`. Tables use sequence PSNR-Y from mean luma MSE and mean SSIM-Y, not a mean of dB values. Full-frame metrics include natural-video letterboxing and white page background; they cannot establish text legibility or perceptual game quality. Hardware frame_type is an MFX bitmask; software frame_type is OpenH264's enum (4 means Skip, not B).

All percentiles use nearest rank. They include startup. A frame's budget is `target_kbps*1000/(8*fps)` bytes. Actual bitrate uses the source's nominal duration, not encode wall-clock throughput. The initial and periodic IDRs count toward bitrate and burstiness. Encoded byte counts include Annex B headers and SEI, and exclude RTP/UDP/IP/SRTP overhead.

For frame i with nominal source time S_i, measured encode service E_i, and size B_i:

```text
encoder_start_i = max(S_i, encoder_finish_(i-1))
A_i = encoder_finish_i = encoder_start_i + E_i
W_i = max(0, D_(i-1) - A_i)
N_i = W_i + 8*B_i/(R_Mbps*1000)       # ms, waiting + own serialization
D_i = A_i + N_i
score_i = E_i + N_i
source_to_drain_i = encoder_start_i - S_i + score_i
```

“E+N P99” is the percentile of the **per-frame sum**, not a sum of separately computed percentiles. It includes the frame's own link drain time. Encoder input wait is reported separately and included in source-to-drain; this matters when software cannot sustain 60 fps. The model keeps all frames, so it exposes backlog rather than assuming unlimited frame dropping. Real operation must replace stale **raw** frames, never discard arbitrary encoded reference frames.

The simple link is evaluated at 8, 12 and 16 Mbps. A separate sensitivity model multiplies elementary-stream bytes by 1.05 to approximate packet/security overhead; it is not measured RTP overhead and includes no retransmission or cross traffic. Configurations are compared at a fixed bitrate target/cadence before using quality as a tie-breaker. Ranking all bitrates together by latency alone would trivially reward starving the encoder and is not a useful quality policy.

Sustained encoder input backlog, sustained link overspend, and excessive skipping make a configuration infeasible at its stated cadence. Do not rank such a run from its service-plus-network score alone: a slower encoder can reduce the network queue while moving the backlog upstream. The source-to-drain and skip columns expose that failure.

## Recommended hardware default

Start **1080p60, LowPower ON, TU7, VBR target=max 10 Mbps on a nominal 12 Mbps link, LowDelayBRC ON, one-frame requested MaxFrameSize, one slice, one reference, Constrained Baseline**. Preserve headroom for packet overhead, retransmissions and short bursts. Treat this as a starting media allocation, not a fixed rate that overrides GCC. If GCC already provides a media-only allocation with overhead accounted for, avoid blindly subtracting the same overhead twice; validate actual wire/pacer behavior.

The normalized configuration below was encoded successfully with **Query=Init=GetVideoParam=0**, with no changes among the recorded fields. Its scrolling bitstream is byte-identical to requesting one-frame VBV and accepting the driver's minimum. All unlisted fields remain zero from initialization. No `mfxExtCodingOption` version-1 buffer is attached; the tested extension set is precisely CodingOption2 + CodingOption3.

```cpp
mfxVideoParam p{};
mfxExtCodingOption2 co2{};
mfxExtCodingOption3 co3{};
co2.Header = {MFX_EXTBUFF_CODING_OPTION2, sizeof(co2)};
co3.Header = {MFX_EXTBUFF_CODING_OPTION3, sizeof(co3)};
mfxExtBuffer* ext[] = {
    reinterpret_cast<mfxExtBuffer*>(&co2),
    reinterpret_cast<mfxExtBuffer*>(&co3)
};
p.ExtParam = ext;
p.NumExtParam = 2;
p.AsyncDepth = 1;
p.IOPattern = MFX_IOPATTERN_IN_VIDEO_MEMORY;
auto& m = p.mfx;
m.CodecId = MFX_CODEC_AVC;
m.CodecProfile = MFX_PROFILE_AVC_CONSTRAINED_BASELINE; // 578
m.CodecLevel = MFX_LEVEL_AVC_42;
m.LowPower = MFX_CODINGOPTION_ON;                    // 16
m.TargetUsage = 7;
m.RateControlMethod = MFX_RATECONTROL_VBR;           // 2
m.TargetKbps = m.MaxKbps = 10000;
m.BufferSizeInKB = 42;
m.InitialDelayInKB = 20;
m.GopPicSize = 65535;
m.GopRefDist = 1;
m.IdrInterval = 0;
m.NumRefFrame = 1;
m.NumSlice = 1;
auto& f = m.FrameInfo;
f.FourCC = MFX_FOURCC_NV12;
f.Width = 1920; f.Height = 1088;
f.CropW = 1920; f.CropH = 1080;
f.FrameRateExtN = 60; f.FrameRateExtD = 1;
f.ChromaFormat = MFX_CHROMAFORMAT_YUV420;
f.PicStruct = MFX_PICSTRUCT_PROGRESSIVE;
co2.AdaptiveI = co2.AdaptiveB = MFX_CODINGOPTION_OFF; // 32
co2.MBBRC = MFX_CODINGOPTION_OFF;
co2.MaxFrameSize = 20833; // floor(10000000 / (8*60)); not a hard guarantee
// IntRefType/CycleSize/QPDelta, MaxSliceSize and QP limits remain 0.
co3.LowDelayBRC = MFX_CODINGOPTION_ON;
// QVBRQuality, IntRefCycleDist, ScenarioInfo, BRCPanicMode,
// WinBRCSize/MaxAvgKbps and MaxFrameSizeI/P remain 0.
```

`GopPicSize=65535` is effectively unbounded for these short sessions, not literally infinite: at 60 fps its period is about 18.2 minutes. Send an on-demand `mfxEncodeCtrl.FrameType = MFX_FRAMETYPE_I | MFX_FRAMETYPE_IDR | MFX_FRAMETYPE_REF` for new viewers, PLI/FIR, resize and window switches, coalescing repeated requests and verifying an IDR in output. Periodic one-second IDRs are not the default.

The VBV fields are capacity/HRD controls, **not** an automatic two-frame encode delay. Immediate synchronized output and measured service time determine latency here. When targeting a different rate/cadence, query and read back the minimum again; never assume one-frame VBV or a retained frame cap is an enforced output bound. Match production BGRA→NV12 conversion and SPS VUI to BT.709 limited as required by the video design; VUI/color integration is outside this encoder-only test.

For this pathological source, LowPower CBR/VBR targets below 16 Mbps can produce roughly 16.6–16.9 Mbps with poor quality. The compatible-profile escape is **LowPower OFF, CBR, LowDelayBRC OFF, MaxFrameSize=0**, keeping TU7, AsyncDepth=1, one reference/slice and no B-frames. At 10 Mbps / 60 fps it controls this source with higher encode cost. At 6.5 Mbps / 60 fps, service time itself accumulates hundreds of milliseconds of input wait; do not select it from E+N alone. Use the measured **30 fps VME variant for the 8 Mbps case**, or reduce resolution/complexity and remeasure. This escape is an observed stress-case mitigation, not evidence that every real game needs VME. GPU rendering contention may change the outcome because VME shares more GPU resources.

## OpenH264 fallback

Use CAMERA_VIDEO_REAL_TIME for unknown/high-motion content. For known scrolling or the tested low-motion 24-fps film, SCREEN_CONTENT_REAL_TIME is a latency-first override with lower detail and much lower achieved bitrate. Switch based on an explicit content policy or measured behavior, not the assumption that every browser frame is easy screen content. Both presets below use RC_BITRATE_MODE, four threads and four fixed slices, one spatial/temporal layer, one reference, and on-demand IDR. Enable frame skipping so rate control can act; report skips and freeze gaps alongside delivered-frame latency.

On texture motion, screen mode with skipping drops 297/600 frames, delivers 30.3 fps, reaches a 200 ms held-frame gap, and scores only 19.22 dB when those held pictures are included. Camera mode at 10 Mbps skips none. Without frame skipping, screen mode produces 15.94 Mbps at a 12 Mbps target. Screen mode’s effective QP range is 26–35; camera mode’s is 12–42. The library also forces scene detection ON and background detection OFF for screen usage. These policy differences are part of the measured usage-mode trade-off.

Four versus eight screen threads/slices on scrolling: encode P99 12.1 versus 12.8 ms; E+N P99 22.3 versus 22.8 ms. One thread/slice gives 15.1 / 23.4 ms. It is a target budget, not a hard frame cap. Screen-mode tweaks reduced skipping on texture motion but still produced roughly 190 ms P99 and poor held-frame quality. Keep the normal 400 ratio and choose the correct usage mode.

Software timing excludes GPU staging readback and BGRA/NV12→I420 conversion. Its low-rate scrolling/film score can beat the hardware partial-path score while spending far fewer bits and giving lower quality; this does not establish a faster real M1 chain. ## Per-scenario overrides and integration boundaries

- **Scrolling:** use the hardware default. If more detail is worth approximately 1.7 ms of partial-path P99, change only CodingOption2.MaxFrameSize to 31250 (VBR1.5 at 10 Mbps). The measured text-region gain is modest. Avoid periodic IDR for normal scrolling.
- **Film/video:** VBR1 stays the latency choice. VBR1.5 gains about 0.36 dB on this film at roughly 4.2 ms additional P99. Prefer 60 fps for active interactive composites; the 30 fps results show a quality/serialization trade-off rather than a universal win. The film's native 24 fps and upscaling limit generalization.
- **Detailed game motion:** keep VBR1 for CB compatibility. If the receiver actually negotiates the corresponding profile, Main (`CodecProfile=77`) or High (`100`) with the same 10 Mbps VBR1 settings reaches 41.83 / 42.47 dB versus CB's 39.99 dB, with approximately 23.5 ms modeled P99 in the single comparison runs. These profile gains are promising; the small latency difference needs repetition. Do not change SPS profile after negotiating CB.
- **Sustained overspend on hard full-screen content:** use the measured VME escape. For a nominal 12 Mbps link, keep 1080p60 but set LowPower=OFF, CBR target=max 10000, CodingOption3.LowDelayBRC=OFF, CodingOption2.MaxFrameSize=0, VBV 42 / initial 20 KB. For an 8 Mbps link, the sustainable measured escape is 1080p30, LowPower=OFF, CBR target=max 6500, level 4.0, VBV 55 / initial 27 KB, MaxFrameSize=0. Keep the remaining baseline fields, including AsyncDepth=1, TU7, one reference/slice and AdaptiveI/B OFF. It gives 6.509 Mbps and 54.6 ms modeled P99 source-to-drain at 8 Mbps (56.0 ms in the 5% overhead sensitivity), with no encoder input backlog. It is not an end-to-end SLO pass.

Always observe actual encoded bitrate and pacer/encoder queue depth. Reset/recreate and on-demand IDR transitions need the real endpoint to validate; these steady ten-second runs do not measure switching cost. A hard timeout/queue policy must replace stale raw frames when necessary. Lower resolution or complexity remains a valid operational response if the real shared GPU/receiver cannot sustain a preset.

## Questions for the real chain

1. **Branded Chrome 89 H.264 receive:** verify 1080p30/60, negotiated CB/Main/High formats, honest SPS levels, hardware versus software decode and decoded/displayed frame counts. The obtainable Chromium 89 binary lacks H.264, as S8 records.
2. **Actual latency SLO:** measure capture/input to displayed pixels over the real 8/12/16 Mbps Wi-Fi/wired path with the intended 50 ms network latency and jitter. This model has zero propagation, no loss/retransmission, no GCC/pacer, and no receiver. Clarify RTT versus one-way 50 ms. Partial-path P99 values cannot establish P80<100/P99<200 ms or be added to other percentiles as a guarantee.
3. **Receiver buffering and loss:** send RTP playout-delay (0,0) as designed and measure M89's result; its JS zero hint alone did not remove its 35–42 ms buffer in S8. Test PLI storms, IDR joins, packet loss/NACK recovery, and whether this intra-refresh bitstream actually provides useful decoder recovery.
4. **Shared GPU and actual input path:** retest Chromium rendering + VPP + encode contention, particularly VME. Measure software staging readback/conversion, encoder/pacer input wait, dropped raw frames and output cadence. The isolated CPU-input software results exclude important costs present in M1.
5. **Live control:** verify GCC SetRates/Reset, bitrate/fps changes, resize and profile renegotiation, first frame after idle, damage-driven variable cadence, repeated joins and recovery after encoder recreation. No changes to those product paths were authorized here.
6. **Quality beyond these proxies:** use native 1080p60 natural video, real rendered games/particles, actual scrolling capture with subpixel text and sticky UI, text readability/subjective comparisons, and longer independent sequences. The current repeats improve tail sampling but do not increase content diversity.

## Chrome 89 compatibility boundary

The interoperability default remains Constrained Baseline, packetization-mode=1, no B-frames, honest SPS level 4.0 for 1080p30 / 4.2 for 1080p60. [The existing negotiation note](g-h264-level.md) found M89 software receive formats CB/Baseline/Main at nominal level 3.1 and profile/packetization matching rather than a receive-side SPS level gate. [S8](s8-chrome89.md) could obtain Chromium 89 without proprietary H.264, so it did **not** prove branded Chrome 89 H.264 decode. Main/High experiments here are quality comparisons, not permission to send those profiles after negotiating CB. High requires a matching explicitly supported receive format.

`MFX_PROFILE_AVC_CONSTRAINED_BASELINE` is **578 (0x242)** in the actual copied headers. The produced hardware SPS in the baseline runs has `profile_idc=66`, constraint byte `0x40`, and level 42/40, i.e. `42402a` / `424028`; this is the Constrained Baseline profile family compatible with the offered `42e01f` profile. Use the macro, not the S7 report's numeric 322. Annex B inspection checks SPS bytes, slice counts, forbidden_zero_bit and file-length/CSV consistency; successful decoded quality comparisons add actual pixel decoding evidence on FFmpeg, not on Chrome 89.

The software presets emit Constrained Baseline `42c02a` at 60 fps, four slices, CAVLC, and no B-slices. Main/High hardware experiments have CABAC PPS flags and no B-slices. These are bitstream observations; negotiation and real receiver decode remain separate checks.
